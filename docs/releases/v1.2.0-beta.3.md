# Maverick v1.2.0-beta.3

Maverick Beta.3 is an experimental prerelease. In plain language, this update
makes configuration mistakes easier to reject safely, makes Profile URI imports
less ambiguous, adds privacy-safe information about the TLS connection actually
used by pooled H2, and strengthens compatibility and release checks. It does not
change the Maverick wire protocol or complete config v2.

This file is a version-specific historical release snapshot. `STATUS.md`
remains the only current product truth and authorization source.

## Highlights

- Configuration loading now checks the version before interpreting the rest of
  a client or server document and returns short, fixed errors for invalid or
  unsupported version metadata.
- Profile URI v1 imports now reject unknown or duplicate decoded query keys and
  ambiguous envelope forms instead of silently choosing one interpretation.
- Pooled H2 shutdown diagnostics can report fixed aggregate classes for the
  outer TLS version and negotiated key-exchange group actually observed.
- Release artifacts gain target-aware CycloneDX SBOM verification, and the
  publication workflow must use this exact version's checked release note.

## Added

### For users and operators

- Fixed, destination-free shutdown counters classify installed physical pooled
  H2 connections as TLS 1.2, TLS 1.3, or unknown, and classify the observed
  key-exchange group as `x25519_mlkem768`, `x25519`, `secp256r1`, `secp384r1`,
  or other/unknown. Cached stream reuse does not increment the connection
  classes again.
- Each supported release target now has a target-aware CycloneDX SBOM alongside
  its archive and checksum.

### For developers

- `maverick_core::config::v2` adds a strict five-axis policy parser, typed
  policy values, a narrow config-v1 Auto/direct-H2 policy projection, and
  value-free typed blocker reasons.
- Compatibility tooling adds same-version and cross-version direct-H2 process
  cells for the fixed Beta.1 and Beta.2 sources, including auth v1 and auth v2
  cases, plus isolated published-artifact upgrade and rollback drills.
- CI adds an independent H3 feature build and focused loopback coverage, plus
  auth-mode tamper and legacy mode-mismatch compatibility witnesses.
- Ordinary Rust tooling is pinned by `rust-toolchain.toml` to Rust 1.97.1. The
  parser-fuzz workflow keeps its separate pinned nightly and cargo-fuzz version.

## Changed / Improved

### For users and operators

- Canonical client and server YAML loading now distinguishes invalid version
  metadata from a well-formed but unsupported version before v1 field parsing.
- The supported config-v1 Auto/direct-H2 subset is checked through the new
  policy projection before selecting the same H2 behavior. Unsupported or
  invalid projection cases retain the legacy selection path; this does not turn
  a v1 document into a runnable v2 document.
- Profile URI secret detection also examines decoded query keys and password
  syntax while retaining a raw-input fallback for malformed command arguments.

### For developers

- SDK client and server YAML helpers now expose the same fixed version-first
  errors as the core parser. Their public function signatures are unchanged.
- CI retains a fail-closed active-document fast path for exact documentation-only
  changes and keeps full Rust, artifact, and local-harness work for other changes.
- Supply-chain checks cover audited dependency and release inputs and verify
  target-aware SBOMs for both supported release targets.
- Release publication stages exactly six named files: the macOS and Linux
  archives, their checksum files, and their SBOMs. The selected release note is
  copied separately, digest-bound, and passed to the release command only after
  final tag and asset rechecks.

## Fixed

- Profile URI v1 rejects unknown decoded keys and every duplicate recognized
  key, including duplicates formed with percent-encoded spellings. A single
  legal percent-encoded spelling of a recognized key remains accepted. User
  information, port syntax, fragments, oversized input, and lossy or ambiguous
  query encodings are rejected with fixed privacy-safe error categories.
- A rejected Profile URI import does not create its requested output file, and
  parser errors do not echo the URI, endpoint, key, value, credential, secret,
  control characters, or long attacker-provided text.
- Release privacy scanning now rejects local-file URI authority forms without
  misclassifying documented neutral linker text.
- The direct-H2 N/N-1 process harness avoids a nonblocking-socket race and keeps
  child-process failure diagnostics metadata-only.

## Security and Privacy

- Config-version and Profile URI failures use fixed short messages rather than
  embedding untrusted input or underlying parser errors.
- TLS observation is counted once per installed physical H2 generation and is
  reported only as fixed aggregate classes. It contains no endpoint, server
  name, destination, credential, path, raw error, stream identifier, or
  per-event timestamp.
- Seeing the `x25519_mlkem768` observation class only means that the client API
  reported that negotiated group on the observed outer H2 TLS leg. It is not a
  post-quantum security guarantee, downgrade proof, cross-leg policy result, or
  end-to-end security claim.
- The release workflow rejects a missing file, a symbolic link, a note larger
  than 64 KiB, a version-heading mismatch, forbidden control bytes, or content
  matching the existing private-path, private-key, or credential patterns.
- Archives contain no shared credentials. Generate fresh local configuration
  with `./maverick gen-config`.

## Compatibility and Migration

- The Maverick protocol version remains `1`. Existing auth v1, auth v2, and
  frame wire formats are unchanged.
- The runnable client/server config version remains `1`, and the stored-client-
  profile schema remains `1`. Beta.2 configurations and current Beta.2 stored
  profiles require no new data migration for Beta.3.
- The stored-profile migration and channel-binding changes published in Beta.2
  are not new Beta.3 changes.
- Strict Profile URI v1 parsing can reject ambiguous inputs that older builds
  tolerated. Remove duplicate or unknown keys and use the canonical
  `maverick://profile/v1` envelope before retrying.
- The new core config-v2 types are additive and marked for forward evolution.
  Complete runnable config-v2 client/server parsing and migration are not part
  of this release. SDK public function signatures are unchanged, but callers
  that compare exact configuration error text should accept the new fixed
  version-first categories.
- The new direct-H2 N/N-1 matrix establishes compatibility only for its complete
  fixed Beta.1/Beta.2 process cells. It does not establish compatibility for
  H3, WebSocket, provider-fronted traffic, every platform, or a real network.

## Removed / Deprecated

None. No public function, wire format, config field, stored-profile field, or
supported release target is removed or deprecated in Beta.3.

## Known Limitations

- A complete runnable config v2 is not implemented. The current v2 work is a
  strict policy parser and a narrow policy-only projection.
- Profile URI v2 is not implemented; the supported URI envelope remains v1.
- Auth v3, complete peer policy confirmation, and per-flow MAC are not
  implemented. The v2 projection does not claim peer confirmation or downgrade
  protection.
- H3 remains experimental and feature-gated. The ordinary config-v1
  Auto/default path remains H2. The policy-only config-v2 parser accepts Auto
  and H2 and rejects H3 as an unavailable capability, but there is no runnable
  config-v2 path. Existing config-v1 experimental H3 behavior remains separate
  and may fall back to H2.
- Provider-fronted H2 is still a TLS-terminating workaround, not native ECH.
  TLS diagnostics describe only the observed client-facing outer leg, not the
  provider-to-origin leg, destination TLS, or an end-to-end property.
- No Stable, mature, production-ready, anonymity, broad censorship-resistance,
  exact browser-equivalence, or provider-independent claim is made.

## Upgrade and Rollback

1. Keep the independently verified Beta.2 archive and configuration as the
   rollback copy.
2. Verify the Beta.3 archive checksum, inner `SHA256SUMS`, `SOURCE.txt`,
   `VERSION.txt`, target, permissions, binary architecture, SBOM, and the
   binary's `version` output before selecting it.
3. Stop the old standalone binary, select the verified Beta.3 folder, and reuse
   the unchanged version-1 configuration. Maverick does not provide an
   installer, updater service, or automatic atomic rollback.
4. To roll back, stop Beta.3 and reselect the independently verified Beta.2
   folder. Do not combine binaries or metadata from different archives.

The repository now contains isolated historical Beta.1-to-Beta.2 upgrade and
rollback drills for macOS and Linux. An exact published Beta.2-to-Beta.3 cycle
cannot be claimed until immutable Beta.3 artifacts exist and that separate
verification is completed.

## Artifacts and Verification

The release workflow builds the two supported pilot targets:

- `aarch64-apple-darwin`
- `x86_64-unknown-linux-gnu`

For each target it verifies an exact seven-entry archive, the outer checksum,
the inner checksums, source revision, version, target, architecture, executable
permissions, fixed public content, and privacy rules. It also generates and
verifies one target-aware CycloneDX SBOM. Publication accepts only the exact six
named archive, checksum, and SBOM files and this digest-bound version-specific
release note.

Repository tests, CI, hashes, SBOMs, local candidate archives, and safe
rejections are quality controls. They are not a human user result, a real-network
result, a production claim, or release authorization. Before publication, the
Beta.3 source is only a local candidate; public Linux/GNU-tar and immutable
release evidence remain pending.
