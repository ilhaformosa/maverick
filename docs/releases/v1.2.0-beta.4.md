# Maverick v1.2.0-beta.4

Maverick Beta.4 is an experimental prerelease. It brings the configuration,
Profile URI, compatibility, transport-diagnostic, and release-integrity work
completed since Beta.2 into one publishable version. It also repairs the
portable macOS CycloneDX verification problem that stopped the Beta.3 release
workflow. It does not change the Maverick wire protocol, enable config v2 for
normal use, or make Maverick production-ready.

The annotated `v1.2.0-beta.3` tag remains as an immutable record of a failed,
fail-closed publication attempt. No Beta.3 GitHub Release or public release
assets were created. Users therefore upgrade directly from the last published
and independently verified Beta.2 release to Beta.4.

This file is a version-specific historical release snapshot. `STATUS.md`
remains the only current product-truth and authorization source.

## Highlights

- Configuration loading checks the version before interpreting the rest of a
  client or server document and returns short, fixed errors for invalid or
  unsupported version metadata.
- Profile URI v1 rejects unknown, duplicate, lossy, or ambiguous input instead
  of silently selecting an interpretation.
- Pooled H2 shutdown diagnostics report privacy-safe aggregate classes for the
  outer TLS version and negotiated key-exchange group actually observed.
- Release archives have target-aware CycloneDX SBOMs, exact six-asset
  publication gates, and a portable verifier used on both Linux and macOS.
- Historical Beta.1/Beta.2 compatibility and published-artifact lifecycle
  drills cover the supported direct-H2 path and honest upgrade/rollback limits.

## Added

### For users and operators

- Fixed, destination-free shutdown counters classify installed physical pooled
  H2 connections as TLS 1.2, TLS 1.3, or unknown. They also classify the
  observed key-exchange group as `x25519_mlkem768`, `x25519`, `secp256r1`,
  `secp384r1`, or other/unknown. Reusing a cached stream does not count the same
  physical connection again.
- Each supported release target includes a target-aware CycloneDX SBOM beside
  its archive and checksum.
- The release note now describes the complete user-visible delta from the last
  published Beta, including upgrade, rollback, compatibility, removals, and
  known limitations.

### For developers

- `maverick_core::config::v2` provides a strict five-axis policy parser, typed
  policy values, a narrow config-v1 Auto/direct-H2 policy projection, and
  value-free typed blocker reasons.
- Compatibility tooling includes same-version and cross-version direct-H2
  process cells for fixed Beta.1 and Beta.2 sources, covering auth v1 and auth
  v2, plus isolated published-artifact upgrade and rollback drills.
- The non-published `maverick-tests` crate includes a pure, no-network v1
  effective-behavior oracle for carrier, trust-route, authentication, shaping,
  and migration-blocker checks. It is verification tooling, not a runtime
  diagnostic, migration engine, SDK, or stable public API.
- CI includes an independent H3 feature build, focused H3 loopback coverage,
  auth-mode tamper checks, and legacy mode-mismatch compatibility witnesses.
- Ordinary Rust tooling is pinned by `rust-toolchain.toml` to Rust 1.97.1. The
  parser-fuzz workflow keeps its separate pinned nightly and cargo-fuzz version.

## Changed / Improved

### For users and operators

- Canonical client and server YAML loading distinguishes invalid version
  metadata from a well-formed but unsupported version before v1 field parsing.
- The supported config-v1 Auto/direct-H2 subset is checked through the new
  policy projection before choosing the same H2 behavior. Unsupported or
  invalid projection cases retain the legacy selection path; this does not
  turn a v1 document into a runnable v2 document.
- Profile URI secret detection examines decoded query keys and password syntax
  while retaining a raw-input fallback for malformed command arguments.

### For developers and release maintainers

- SDK client and server YAML helpers expose the same fixed version-first errors
  as the core parser. Their public function signatures are unchanged.
- CI keeps the fail-closed documentation-only fast path for exact documentation
  changes and runs the full Rust, artifact, and local-harness work for other
  changes.
- Supply-chain checks cover audited dependencies and release inputs, and verify
  target-aware SBOMs for both supported release targets.
- Publication accepts exactly the macOS and Linux archives, their checksum
  files, and their target-aware SBOMs. The version-specific release note is
  copied separately, digest-bound, and rechecked before publication.
- CycloneDX dependency-reference verification now compares the root/component
  and dependency reference sets in separate portable steps. It requires a
  dependency array, an object with a string `ref` in every entry, and exact set
  equality with the root and component references. Errors remain fixed and
  privacy-safe and do not expose raw SBOM content, paths, or environment
  details. This repairs the macOS verifier inconsistency that stopped the
  Beta.3 workflow without weakening the graph check.

## Fixed

- Profile URI v1 rejects unknown decoded keys and every duplicate recognized
  key, including duplicates created with percent-encoded spellings. A single
  legal percent-encoded spelling of a recognized key remains accepted.
- Profile URI user information, invalid port syntax, fragments, oversized
  input, and lossy or ambiguous query encodings are rejected with fixed
  privacy-safe categories.
- A rejected Profile URI import does not create its requested output file, and
  errors do not echo the URI, endpoint, key, value, credential, secret, control
  characters, or long attacker-provided text.
- Release privacy scanning rejects private local-file URI authority forms
  without misclassifying documented neutral linker text.
- The direct-H2 N/N-1 process harness avoids a nonblocking-socket race and keeps
  child-process failure diagnostics metadata-only.
- Target-aware SBOM verification behaves consistently on supported Linux and
  macOS shells for the same valid graph-reference sets.

## Security and Privacy

- Config-version and Profile URI failures use fixed short messages instead of
  embedding untrusted input or underlying parser errors.
- TLS observation is counted once per installed physical H2 generation and is
  reported only as fixed aggregate classes. It contains no endpoint, server
  name, destination, credential, path, raw error, stream identifier, or
  per-event timestamp.
- The `x25519_mlkem768` observation class means only that the client API
  reported that negotiated group on the observed outer H2 TLS leg. It is not a
  post-quantum guarantee, downgrade proof, cross-leg policy result, or
  end-to-end security claim.
- The release workflow rejects missing, symbolic-link, oversized, malformed,
  version-mismatched, control-byte-bearing, or privacy-sensitive release input.
- Archives contain no shared credentials. Generate fresh local configuration
  with `./maverick gen-config`.

## Compatibility and Migration

- The Maverick protocol version remains `1`. Existing authentication and frame
  wire formats, including auth v1 and auth v2, are unchanged.
- The runnable client/server config version and stored-client-profile schema
  both remain `1`.
- Exact-known Beta.2 configuration and stored-profile data require no new
  migration for Beta.4. The explicit stored-profile channel-binding migration
  introduced in Beta.2 remains the supported path for older flat profiles.
- Strict Profile URI v1 parsing can reject ambiguous input that older builds
  tolerated. Remove duplicate or unknown keys and use the canonical
  `maverick://profile/v1` envelope before retrying.
- The config-v2 types are additive and marked for forward evolution. Complete
  runnable config-v2 parsing and migration are not part of this release.
- No public function signature is removed. Callers that compare exact
  configuration error strings should accept the new fixed version-first
  categories.
- The direct-H2 N/N-1 matrix establishes compatibility only for its complete,
  fixed Beta.1/Beta.2 process cells. It does not establish compatibility for
  H3, WebSocket, provider-fronted traffic, every platform, or a real network.

## Removed / Deprecated

None. No public function, wire format, config field, stored-profile field, or
supported release target is removed or deprecated in Beta.4.

## Known Limitations

- A complete runnable config v2 is not implemented. The current v2 work is a
  strict policy parser and a narrow policy-only projection.
- Profile URI v2 is not implemented; the supported URI envelope remains v1.
- Auth v3, complete peer policy confirmation, and per-flow MAC are not
  implemented. The v2 projection does not claim peer confirmation or downgrade
  protection.
- H3 remains experimental and feature-gated. The ordinary config-v1
  Auto/default path remains H2. The policy-only config-v2 parser accepts Auto
  and H2 and rejects H3 as an unavailable capability, but there is no runnable
  config-v2 path. Existing config-v1 experimental H3 behavior remains separate
  and may fall back to H2.
- Provider-fronted H2 remains a TLS-terminating workaround, not native ECH.
  TLS diagnostics describe only the observed client-facing outer leg, not the
  provider-to-origin leg, destination TLS, or an end-to-end property.
- SBOMs describe resolved build inputs. They are not provenance attestations,
  signatures, reproducible-build proof, or a software-safety guarantee.
- No Stable, mature, production-ready, anonymity, broad censorship-resistance,
  exact browser-equivalence, or provider-independent claim is made.

## Upgrade and Rollback

1. Keep the independently verified Beta.2 archive and configuration as the
   rollback copy.
2. Download the Beta.4 archive, checksum, and matching target-aware SBOM. Verify
   the outer checksum, inner `SHA256SUMS`, `SOURCE.txt`, `VERSION.txt`, target,
   permissions, binary architecture, SBOM, and binary `version` output.
3. Stop the old standalone binary, select the verified Beta.4 folder, and reuse
   the unchanged version-1 configuration. Maverick has no installer, updater
   service, or automatic atomic rollback.
4. Run `./maverick user-smoke` before ordinary use. Do not combine binaries or
   metadata from different archives.
5. To roll back, stop Beta.4 and reselect the independently verified Beta.2
   folder and its matching metadata.

Beta.3 has no public assets and is not an upgrade or rollback point. The
repository contains isolated historical Beta.1-to-Beta.2 published-artifact
upgrade and rollback drills for the supported platforms. Beta.2-to-Beta.4 is
not a published lifecycle result unless immutable Beta.4 assets exist and the
separate public verification succeeds.

## Artifacts and Verification

The release workflow builds two supported pilot targets:

- `aarch64-apple-darwin`
- `x86_64-unknown-linux-gnu`

Each target has one exact seven-entry archive, one outer checksum, and one
target-aware CycloneDX SBOM. The six release assets are therefore the macOS
archive, checksum, and SBOM, plus the Linux archive, checksum, and SBOM. The
workflow checks source revision, version, target, architecture, permissions,
fixed public content, inner and outer checksums, SBOM structure, and privacy
rules. This release note is not a seventh asset: the workflow takes a private
snapshot, binds its digest, and uses that exact content as the GitHub Release
body.

Repository tests, CI, hashes, SBOMs, local candidate archives, and safe
rejections are quality controls. They are not a human user result, real-network
result, production claim, or publication by themselves. Until the annotated
Beta.4 tag, public prerelease, exact assets, and independent verification all
succeed, Beta.2 remains the current published release.
