# Maverick v1.2.0-rc.1

Maverick RC.1 is an experimental prerelease candidate for the Direct HTTP/2
route. It is not a Stable or production-ready release. The ordinary product
path remains browser-like TLS 1.3 over HTTP/2, and the protocol, runnable
configuration, stored-profile, authentication, and frame wire versions remain
`1`.

This candidate deliberately favors a smaller proven product over unfinished
transport expansion. H3 remains disabled, the retired Quinn implementation is
absent, and quiche is used only by unpublished candidate tests. The
provider-fronted H2 route remains Beta and is not part of the first Stable
support claim.

## Highlights

- Makes Direct TLS/H2 the only route evaluated for the first v1.2 Stable
  support claim.
- Retires the old config-v1 Quinn H3 product path instead of carrying two H3
  implementations.
- Strengthens bounded H2 connection, relay, timeout, shutdown, target-admission,
  and privacy-safe diagnostic behavior.
- Adds fail-closed RC tag and artifact verification while keeping publication
  as a separate decision.
- Preserves `v1.2.0-beta.4` as the immutable rollback partner.

## User-Visible Changes Since Beta.4

### Direct H2 reliability

- The client H2 pool has bounded checkout, idle retirement, shutdown, and
  timeout behavior. Authentication failure is not silently retried on another
  connection.
- Upload and download progress use bounded no-progress timeouts instead of
  allowing stalled relay work to live forever.
- TCP, HTTP CONNECT, SOCKS5, DNS relay, and UDP relay paths keep fixed flow and
  resource limits and release their work on cancellation or terminal failure.
- Server target resolution and connection attempts have explicit timeout and
  privacy-safe metric categories. Default target policy rejects reserved or
  unsafe address ranges.
- Fallback responses retain fixed, protocol-neutral shapes and do not expose
  authentication or parser details.

### Transport scope

- Direct browser-like TLS 1.3 + HTTP/2 is the RC route.
- Provider-fronted H2 remains available as a Beta route with a different trust
  boundary: the provider terminates TLS and can observe authentication data and
  tunneled traffic.
- The older WebSocket carrier remains a compatibility path.
- Config-v1 H3 requests fail closed before product network I/O. The unpublished
  Quinn H3 implementation and dependencies were removed.
- quiche qualification and private-patch experiments remain test-only. They do
  not enable H3, QUIC Datagram, Auto H3, or a second product backend.

### Release safety

- RC tags must be annotated, point directly at the reviewed commit, match the
  Cargo package version, and remain on the main history.
- RC artifacts use the same fixed macOS and Linux archive, checksum, and
  target-aware CycloneDX SBOM shape as the Beta release train.
- Artifact verification checks version, source revision, target, architecture,
  permissions, fixed public files, checksums, SBOM structure, and native binary
  identity where the host matches.
- Release notes are version-bound, privacy-scanned, copied to a private
  snapshot, and digest-checked again before publication.
- An RC GitHub Release is a prerelease and is never Latest.

## Compatibility

- Maverick protocol version: `1`.
- Runnable client/server configuration version: `1`.
- Stored client-profile schema version: `1`.
- Existing authentication and frame wire formats are unchanged.
- Existing valid Beta.4 v1 configuration is intended to remain usable by RC.1.
- Provider-fronted H2 and WebSocket remain Beta/compatibility routes and cannot
  satisfy a Direct-H2 Stable gate.
- Config v2, auth v3, Profile URI v2, Auto H3, and native QUIC Datagram are not
  part of this candidate.

The exact RC-to-Beta.4 compatibility and native rollback exercises are release
gates. They are not considered complete merely because this candidate or this
release note exists.

## Security and Privacy Boundaries

- This candidate does not claim anonymity, exact browser fingerprint
  equivalence, provider independence, native ECH, broad censorship resistance,
  or safety for at-risk third parties.
- Logs and diagnostics remain bounded and avoid endpoints, credentials, raw
  attacker input, packet contents, and environment-specific details.
- Authentication, trust-route selection, target admission, resource budgets,
  and failure behavior remain fail closed.
- No failure is allowed to silently retry authentication, replay or duplicate
  application data, cross a trust route, or switch to H3.
- Candidate-only tests, hashes, SBOMs, and CI are quality evidence, not a
  production-readiness or real-network result.

## Known Limitations

- RC.1 is still Beta-quality software under evaluation. Stable gates are not
  automatically satisfied by publishing an RC.
- H3 and native QUIC Datagram are unavailable in the product.
- Provider-fronted H2 is not native ECH and exposes a different trust route.
- Maverick has no automatic installer, updater, or atomic rollback service.
- SBOMs describe resolved inputs; they are not signatures, provenance
  attestations, reproducible-build proof, or a software-safety guarantee.
- A new exact-candidate security review, supported-target artifacts, public CI,
  field observation, and rollback exercise are required before Stable can be
  considered.

## Upgrade and Rollback

This file accompanies candidate preparation; it does not mean RC.1 has already
been published. After publication, use only the archive, checksum, and
target-aware SBOM belonging to the same target and release.

1. Keep the independently verified Beta.4 archive and a backup of the version-1
   configuration as the rollback copy.
2. Verify the RC.1 archive checksum, inner `SHA256SUMS`, `SOURCE.txt`,
   `VERSION.txt`, target, permissions, SBOM, and binary `version` output.
3. Stop the old standalone binary, select the verified RC.1 folder, and reuse
   the unchanged version-1 configuration.
4. Run `./maverick user-smoke` before ordinary use.
5. To roll back, stop RC.1 and reselect the independently verified Beta.4
   folder and matching metadata. Do not mix files from different releases.

The owner field observation and native rollback exercises are separate gates
and will be recorded only after they actually occur.
