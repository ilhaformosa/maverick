# Maverick v1.2.0-rc.2

Maverick RC.2 is an experimental security-maintenance prerelease for Direct
TLS 1.3 + HTTP/2. It is not Stable or production-ready. H3 remains disabled;
provider-fronted H2 remains Beta and outside the first Stable support claim.
Protocol, runnable configuration, and stored-profile formats remain version 1.

## Changes since RC.1

- Upgrade rustls to 0.23.46, rustls-webpki to 0.103.16, webpki-roots to 1.0.10,
  and Tokio to 1.53.3. These address RUSTSEC-2026-0346 through
  RUSTSEC-2026-0349, RUSTSEC-2026-0381, RUSTSEC-2026-0382, and the
  RUSTSEC-2026-0386 soundness warning without advisory exceptions.
- Reject nonstandard Brotli large-window certificate streams in the default
  browser TLS path. Strict decoding also rejects incomplete and trailing data
  while retaining the output limit. This closes the same excessive-allocation
  behavior in Maverick's custom decoder that the rustls update addresses in
  its optional decoder.
- Replace the YAML parser with the maintained safe-Rust serde-saphyr parser,
  preserving the documented version-1 configuration and privacy-safe errors.
- Keep private-mode clients restricted to browser TLS. The compatibility suite
  now tests successful private-mode connections with browser TLS and explicit
  rejection of the rustls fingerprint in both build variants.
- Update the Linux-only TUN test harness to Tokio's explicit registration API.
  This does not enable or deploy TUN functionality.

## Compatibility and limitations

Authentication and frame wire formats are unchanged. Existing valid version-1
configuration remains the supported input. Certificate chains through the
distrusted intermediates covered by the new WebPKI advisories are rejected;
certificate pinning does not bypass normal trust validation.

This candidate does not introduce H3, native QUIC Datagram, Auto H3, native
ECH, or a new trust route. It does not claim anonymity, browser fingerprint
equivalence, provider independence, or broad censorship resistance. The
provider-fronted route terminates TLS at the provider and retains its existing
privacy tradeoff.

Local tests, CI, security review, artifact checks, and automated rollback
drills do not constitute owner field use. A new 72-hour observation and owner
rollback experience are still required before Stable can be considered.

## Upgrade and rollback

Use matching archive, checksum, and target-aware SBOM files for either Apple
Silicon macOS or x86-64 GNU/Linux. Verify the archive checksum, inner
`SHA256SUMS`, version, source revision, target, and binary identity before use.
Do not mix files from different releases.

Back up the version-1 configuration, stop the old standalone binary, select
the verified RC.2 directory, and run `./maverick user-smoke` before ordinary
use. No system proxy, DNS, route, or interface change is part of installation.

The fixed compatibility rollback partner remains `v1.2.0-beta.4`. It and RC.1
do not acquire these security fixes retroactively; rollback restores earlier
behavior, not the patched dependency set. Keep rollback use confined to the
owner-controlled validation environment and do not treat it as a security
upgrade.
